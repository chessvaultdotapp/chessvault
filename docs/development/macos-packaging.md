# macOS app bundle staging

`tools/dist-prepare/macos.py` stages a standalone `ChessVault.app`. It does not build
Rust code, sign, notarize, archive, or publish the app. Linux staging
remains in `tools/dist-prepare/linux.py`.

## Inputs

- A release-mode macOS executable, initially targeting `aarch64-apple-darwin`.
- The `chessvault.icns` generated by `apps/chessvault/build.rs` in Cargo's `OUT_DIR`.
  It renders the SVG logo into standard and Retina PNG-backed ICNS entries, up to
  1024×1024, on every build host. PNG or SVG files cannot simply be renamed to `.icns`.
  Locate the output using Cargo's `--message-format=json` build-script messages;
  release automation must copy/pass that generated file to the packager.
- Numeric display and build versions, with one to three dot-separated components.
  Git tags, prerelease suffixes, and SemVer build metadata are not accepted as
  Apple bundle versions. Release automation must choose the numeric mapping.
- The minimum macOS version used when compiling the executable. Set
  `MACOSX_DEPLOYMENT_TARGET` at build time and pass the same value to the packager;
  writing `Info.plist` does not lower the executable's actual deployment target.

For example, **if the binary was built with a deployment target of 13.0**:

```sh
python3 tools/dist-prepare/macos.py target/aarch64-apple-darwin/release/chessvault \
    --icon /path/to/chessvault.icns \
    --version 0.1.0 --build-version 1 --minimum-macos 13.0 \
    --output dist/ChessVault.app
```

This example does not establish macOS 13 as a tested compatibility baseline.

## Bundle contents

```text
ChessVault.app/
└── Contents/
    ├── Info.plist
    ├── MacOS/
    │   └── chessvault
    └── Resources/
        ├── chessvault.icns
        └── LICENSE
```

The bundle identifier is `app.chessvault.ChessVault`. Executable and directory
permissions are normalized to 0755; resource files use 0644. Existing outputs,
including dangling symlinks, are rejected. Staging uses a temporary sibling and
renames only after all files have been written; ordinary staging failures leave
no partial bundle. Inputs are not modified.

## Signed ZIP packaging on macOS

`tools/dist-prepare/package_macos.py` runs on macOS with Xcode command-line tools.
It consumes the same binary, icon, and explicit version/deployment metadata as the
staging tool. It does not build Rust code or publish a release.

```sh
python3 tools/dist-prepare/package_macos.py target/aarch64-apple-darwin/release/chessvault \
    --icon /path/to/chessvault.icns \
    --version 0.1.0 --build-version 1 --minimum-macos 13.0 \
    --output dist/ChessVault-macos-aarch64.zip
```

The CI job currently uses 13.0 as a provisional deployment baseline, not a verified
runtime support guarantee. The driver:

1. Uses `lipo` to require an arm64-only executable.
2. Uses `otool` to require the declared deployment target to match the Mach-O
   target and rejects linked libraries outside `/System/Library` and `/usr/lib`.
   Non-system libraries, including `@rpath` references, are not bundled automatically.
3. Decodes the ICNS with `iconutil`, stages the app, and checks the plist with `plutil`.
4. Ad-hoc signs the completed bundle with `codesign` (no credentials or timestamp)
   and verifies its signature with strict checks.
5. Archives with `ditto --sequesterRsrc --keepParent`, extracts to a temporary
   directory, and smoke-checks the extracted app before publishing the ZIP:
   verify its signature, expected bundle/version/deployment metadata, nonempty
   executable/icon/license files, and preserved executable permission.

This is a package-integrity smoke check, comparable to Linux's native archive
installer checks and AppImage extraction/content checks. It does not launch the
GUI or attempt a broad OS compatibility matrix.

Existing outputs are rejected. Temporary bundle/archive files are removed on ordinary
failures; the destination ZIP appears only after all checks pass. The source binary
is never signed or modified. This initial driver does not support Intel/universal
binaries or copy non-system dynamic libraries. Linked-library checks do not detect
all runtime-loaded dependencies and are not a substitute for testing on a clean Mac.

## Release artifact builds

The development and stable release workflows each define a `build-macos` job
on Apple Silicon `macos-15`. Both jobs use the same Python packaging tools.
Stable macOS packaging is currently disabled pending manual acceptance testing.
It builds the locked release executable for `aarch64-apple-darwin`
with `MACOSX_DEPLOYMENT_TARGET=13.0` and runs the full packaging driver with real
Apple tools. This is a provisional baseline; building on macOS 15 does not verify
that the GUI works on macOS 13. The locked wgpu-hal Metal backend documents a
macOS 10.13 minimum, below this baseline, but other dependencies and runtime
behavior still need acceptance testing on the intended minimum OS.

`ci_macos.py` reads the executable and ICNS locations from Cargo JSON messages,
matching the desktop package ID from Cargo metadata. It supports custom target
directories rather than guessing a build-script hash. Bundle versions are:

- `CFBundleShortVersionString`: Cargo's numeric `major.minor.patch`, with prerelease
  and build suffixes removed.
- `CFBundleVersion`: the CI run number encoded as
  `1 + run_number / 10000`, `(run_number / 100) % 100`, and `run_number % 100`
  using integer division. This fits Apple's four/two/two digit component limits
  for run numbers 1 through 99,989,999. For example, run 12,345 becomes `2.23.45`.
- Reruns keep the bundle version. Each caller workflow has its own run-number
  counter, so build versions are not globally unique or monotonic across
  development and stable releases.
  No in-app update mechanism relies on these numbers.

The build job uploads the versioned app ZIP inside a seven-day workflow artifact;
only the publishing job uploads it to GitHub Releases. For manual testing, download
that artifact from the release workflow run and extract the outer GitHub artifact
archive, then the inner app ZIP. Ordinary Rust CI keeps macOS build, test, lint,
and differential checks, but does not package the app.

## Release downloads

Both `development-release.yml` and `stable-release.yml` run their inline macOS
packaging job in parallel with their existing Linux builds. The tagged
Cargo version must exactly match the release tag (`v<Cargo version>`), including
prerelease and build suffixes, before packaging succeeds. Bundle versions use the
same numeric mapping above, with the caller release workflow's run number.

Development publication waits for both platforms and verifies all three final assets:

- `chessvault-<tag>-linux-x86_64.tar.gz`
- `chessvault-<tag>-linux-x86_64.AppImage`
- `chessvault-<tag>-macos-aarch64.zip`

Stable releases currently publish Linux assets only. The stable workflow retains
the macOS job behind `identify-tag.env.MACOS_ENABLED: 'false'`. Changing this single
flag to `'true'` enables macOS packaging, required asset checks, upload, and the
release-note warning. A skipped, disabled macOS job does not block Linux publication;
an enabled macOS job must succeed before publication. Enable it only after manual
acceptance testing of the downloaded development app on the intended macOS versions.

Only publishing jobs have write permission. Existing assets are not overwritten
on reruns; tag filtering and release retention rules remain unchanged. No Apple
secrets are needed. Releases that include macOS assets include an Apple Silicon/unnotarized warning
and identify macOS 13.0 as a provisional deployment target.

Download the macOS ZIP from the project's trusted GitHub release page, compare
its SHA-256 hash with GitHub's asset digest, and extract it using Archive Utility.
Move `ChessVault.app` to Applications if desired. The app is ad-hoc signed, not
Developer ID signed or notarized; Gatekeeper may block downloaded copies.
Consult Apple's current instructions for opening an app from an unidentified
developer only after verifying the download and deciding to trust it. Do not
disable Gatekeeper globally. Intel Macs are not supported by this archive.

## Validation and next steps

Run layout and CLI tests on Linux or macOS without a Rust build:

```sh
just --justfile venvs/justfile dist-prepare
venvs/dist-prepare/bin/python -m pytest tools/dist-prepare -q
```

The packager deliberately treats binary and icon contents as opaque. Tests verify
layout, metadata, permissions, existing-output rejection, and failure cleanup,
not Mach-O architecture, linked-library portability, or ICNS validity. The desktop
integration test `distribution_icon` separately checks the generated ICNS container,
entry sizes, and PNG decoding on any host:

```sh
cargo test -p chessvault --test distribution_icon --locked
```

The packaging driver's orchestration and failure paths are tested with stand-ins
for Apple tools on any host. The macOS release packaging job exercises real tools;
manual artifact testing is still required before claiming runtime compatibility,
particularly on the provisional minimum OS. Release workflows do not exercise
Finder launch or GUI interactions.

Developer ID signing and notarization are deferred; ad-hoc signing alone does not
establish a trusted publisher or satisfy Gatekeeper's normal downloaded-app checks.
A Gatekeeper assessment is not expected to pass for these unnotarized downloads.

Manual acceptance testing must include launching from Finder outside the checkout,
board rendering and input, resizing, and closing/reopening to restore window state.
Native release state lives under `$XDG_STATE_HOME/chessvault` when the override
is absolute, otherwise `~/Library/Application Support/chessvault`. Logs remain
under `~/Library/Logs/chessvault` regardless of XDG overrides. Do not infer native release behavior from
development-mode debug builds.
